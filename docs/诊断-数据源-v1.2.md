# 诊断：数据源 v1.2（为什么数据会变）

日期：2026-11-16
结论：当前 8000 是**契约 SQLite 种子服**；旧前端截图里的 `吴开风/高二(2)班`、v1.1 截图里的 `林清和` 都**不在这套库**。数据变化来自 8000 上后端进程切换，不是新旧前端在改数据。

|---|---|---|

旧前端与新前端 `vite.config.ts` 都代理 `http://127.0.0.1:8000`，所以“旧前端有旧数据、新前端有新数据”不是请求路径差异，而是**8000 上曾启动过不同后端**（生产 MySQL 或另一份 contract.db 种子）。

## 四、401 的直接原因

- 契约服 `serve_contract.py` 第 42 行硬编码 `SECRET_KEY="contract-demo-secret-key-please-do-not-use-in-prod"`；生产根 `.env` 是另一套。同一浏览器 token 在两套后端之间切换，签名验证必失败。
- 截图请求：`POST http://127.0.0.1:5174/api/v1/auth/logout` → 401，referrer `teacher/classes`，请求头**没有** `Authorization`。
- 前端 `authApi.logout()` 只设 `skipGlobalError: true`，未设 `skipAuthRedirect: true`；`auth.logout()` 无论有无 token 都发请求；`main.ts` 的 session-expired 只 `auth.clear()`，不清 `currentClassId`。

## 五、为什么旧数据今晚拿不回来

- 旧数据大概率在生产 MySQL；本机 3306 可连，但多组凭据 1045。
- Redis 6379 不监听；Docker Desktop 引擎管道不存在，`com.docker.service` 停止且当前用户无法启动（需管理员）。
- 因此不能“把旧 MySQL 数据搬到 8000”；也不应该为了演示重置 root 或改库。

## 六、恢复旧数据的前置（本轮不执行）

1. 以管理员启动 Docker Desktop / `com.docker.service`，确认 `dockerDesktopLinuxEngine` 管道可用。
2. 使用仓库 `deploy/docker-compose.dev.yml` 的 MySQL/Redis 端口（如 13306/16379），不要占用 3306/6379 与本机服务冲突。
3. 或提供可登录的 MySQL 账号/密码（只读即可），由后端脚本做只读对照。
4. 恢复前先备份 `contract.db` 与目标 MySQL；**不得重置、不得删表**。
5. 恢复后停掉 8000 契约服，避免 8000 同时被两套后端争用；前端清 `sproutlearn.v3.auth.token` / `user` / `sprout.v3.currentClassId` 再登录。

## 七、v1.2 决策

- 录制期间 8000 只跑契约 SQLite；不启动 MySQL 后端抢 8000。
- 契约服重启必须带 `CONTRACT_PORT=8000`；否则默认 8010，5174 会 500。
- 前端启动必须校验 `/auth/me`；旧 class_id 必须按当前 `/classes` 校验；quote 失败不显示本地兜底。
- 旧数据恢复另立任务，不在今晚硬做；如果演示必须用旧班数据，需要用户先解决 Docker/凭据。
